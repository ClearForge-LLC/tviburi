# Harden the H7, then follow Renode's seams

The families that add the most value to Aethelgard and Tviburi are not the ones with the most features but the ones that bring a **new failure class on top of a Renode base that already exists**, so the honesty work can start at once. In order, that means finishing the STM32H753/H743 (whose stock platform still serves 38 tagged blocks and two "always ready" Python stubs); then nRF52840 (radio, PPI, multi-node), STM32F405/F407 (flight-controller breadth), LiteX on iCE40/ECP5 (the peripheral is the user's own RTL) and i.MX RT1062 (clock tree and caches), each of which has an official or close-sibling Renode platform; then STM32G4, STM32U5/H5, nRF54L15, H723/F7, RP2040, ESP32-S3 and AT32F435, which need new platform files and models on CPU cores Renode already has; and last TI C2000, dsPIC33, RP2350, ESP32-C6, i.MX RT1176 and nRF54H20, which Renode cannot host without a new CPU core or a greenfield SoC. SAM E70 adds almost nothing new and is worth only a cheap audit. The finding with the biggest consequence is that **no published simulator or research system refuses unmodeled hardware**: Renode, QEMU and the firmware-rehosting literature all default to "read zero, log, keep going" or actively invent plausible answers, so Tviburi's refuse-by-name contract is new ground. A separate chipset-agnostic twin project becomes necessary the first time Scotty schedules a target Renode has no CPU or SoC base for, or the first time refusal must hold the same way across two simulators; it should be a register-truth layer generated from SVD (and EDC, TargetDB and csr.json), with adapters into Renode, QEMU and others, not a new emulator. Two warnings before relying on any of this: every Renode fact in the notes was read from master `c38ac3b` (2026-11-20), not the `ab721d88` tag Aethelgard pins as 1.17.0, and the RM0433 revision conflict (Rev 8 versus the Rev 9 held on Furnace) is unresolved.

## Renode's honesty gap sits in the registers, not the CPUs

Renode's CPU cores come from tlib, Antmicro's LGPL fork of QEMU's TCG ([antmicro/tlib](https://github.com/antmicro/tlib)), and Cortex-M dominates the shipped platforms with **63 `CortexM` references across the `.repl` files**, against 19 each for RiscV64 and ARMv8A ([renode platforms](https://github.com/renode/renode/tree/master/platforms)). For a Cortex-M7 such as the STM32H753, the honest-twin problem is therefore almost entirely a peripheral problem.

Renode documents four modelling tiers: automatic tags from SVD "used mainly for logging purposes", manual tags that return fixed values, IronPython peripherals, and full C# models ([renode-docs writing-peripherals](https://github.com/renode/renode-docs/blob/master/source/advanced/writing-peripherals.md)). For an address with no peripheral, "the default value of 0 will be returned and a warning message will be generated", and the logger documentation recommends `sysbus SilenceRange` to quiet those warnings ([renode-docs logger.md](https://github.com/renode/renode-docs/blob/master/source/basic/logger.md)). **The documented posture is to silence the unmodeled, not to fail on it.**

A strict switch exists, but only for addresses with nothing behind them. `SystemBus` exposes `UnhandledAccessBehaviour` with the values `Report`, `ReportIfTagged`, `ReportIfNotTagged`, `DoNotReport`, `ThrowException` and `ThrowExceptionIfNotTagged`, and each tag also takes a `throwException` flag; when either fires, the bus raises `BusAccessException(AddressError)` ([UnhandledAccessBehaviour.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Main/Peripherals/Bus/UnhandledAccessBehaviour.cs); [SystemBus.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Main/Peripherals/Bus/SystemBus.cs)). Inside a mapped C# model nothing throws. `RegisterCollection.Read` on an unknown offset logs and returns `default(T)` ([RegisterCollection.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Main/Core/Structure/Registers/RegisterCollection.cs)), and `PeripheralRegister` warns that unhandled fields "have to be tagged. Otherwise, they will not be logged" ([PeripheralRegister.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Main/Core/Structure/Registers/PeripheralRegister.cs)). **That register tier is exactly the hole Tviburi's refusing subclasses fill**, and no stock setting closes it.

Releases come roughly every six to seven months, 1.16.0 (2025-08-02), 1.16.1 (2026-02-16) and then **1.17.0 (2026-09-06)** ([CHANGELOG.rst](https://raw.githubusercontent.com/renode/renode/master/CHANGELOG.rst)), and coverage changes between them. Timer input capture arrived only in 1.17.0 ([CHANGELOG.rst](https://github.com/renode/renode/blob/master/CHANGELOG.rst)), so firmware that relied on it under 1.16.x ran on silently wrong behaviour. Pinning the Renode version is a fidelity control, not housekeeping.

### Phases 0 and 1 reuse platforms Antmicro already maintains

**The H753 comes first because its gaps can be listed by machine.** `stm32h753.repl` is `stm32h743.repl` plus one `STM32H7_CRYPTO`, and the shared H7 file models only SPI4 even though an `STM32H7_SPI` class exists, while Tagging SPI1/2/3/5/6, MDMA, HRTIM, DFSDM1, SAI1–4, OPAMP, COMP1–2 and DAC1 ([stm32h7.repl](https://github.com/renode/renode/blob/master/platforms/cpus/stm32h7.repl); [stm32h753.repl](https://github.com/renode/renode/blob/master/platforms/cpus/stm32h753.repl)). ArduPilot carries **about 121 H743 hwdefs and about 66 F405**, and PX4 has 60 STM32H7 family configs against 6 for the F405RG ([ArduPilot hwdef](https://github.com/ArduPilot/ardupilot/tree/master/libraries/AP_HAL_ChibiOS/hwdef); [PX4 boards](https://github.com/PX4/PX4-Autopilot/tree/main/boards)), so H743 is nearly free once H753 refusals exist. The F405/F407 is cheap breadth: `stm32f4.repl` models USART, SPI1–3, I2C1–3, CAN, DMA, TIM1–14, RCC and PWR, but Tags USB, declares no ADC and includes an Ethernet MAC ([stm32f4.repl](https://github.com/renode/renode/blob/master/platforms/cpus/stm32f4.repl)) that the notes say, from memory, the F405 lacks, so a strict F405 twin must refuse that block once RM0090 confirms it.

**nRF52840 is the cheapest door into radio honesty.** It is the only Nordic or NXP part here with a hand-written official platform, with RADIO, PPI, TIMER, RTC, GPIOTE, EGU and UARTE models ([nrf52840.repl](https://github.com/renode/renode/blob/c38ac3babcd38a7144b9498e3ca4c2226b76aa37/platforms/cpus/nrf52840.repl)) and a working two-node Zephyr BLE script that requires `SetGlobalQuantum "0.00001"` ([nrf52840-ble-zephyr.resc](https://github.com/renode/renode/blob/c38ac3babcd38a7144b9498e3ca4c2226b76aa37/scripts/multi-node/nrf52840-ble-zephyr.resc)). The radio model's own source supplies the refusal list: MODE is "just RW", transmit times "assume 1M PHY", whitening and CCA thresholds are Tagged, and the `EndStart` short is unsupported because "it's instant from our perspective" ([NRF52840_Radio.cs](https://github.com/renode/renode-infrastructure/blob/09ac7c563095c5410258ecc1b1a6b841a013db85/src/Emulator/Peripherals/Peripherals/Wireless/NRF52840_Radio.cs)). No NRF model implements System OFF either ([NRF_CLOCK.cs](https://github.com/renode/renode-infrastructure/blob/09ac7c563095c5410258ecc1b1a6b841a013db85/src/Emulator/Peripherals/Peripherals/Miscellaneous/NRF_CLOCK.cs)).

**LiteX on Lattice FPGAs is the cheapest new architecture and carries the strongest honesty claim of any candidate.** Renode ships about fifteen LiteX platforms, an iCE40 board file, and Verilator/DPI co-simulation over AXI, APB3, AHB and Wishbone, so the twin can run the user's own RTL as the peripheral ([renode platforms/cpus](https://github.com/renode/renode/tree/master/platforms/cpus); [co-simulation docs](https://renode.readthedocs.io/en/latest/advanced/co-simulating-with-an-hdl-simulator.html)). LiteX exports SVD and `csr.json` from the same design it synthesises, so specification, RTL and register map cannot drift apart ([export.py](https://github.com/enjoy-digital/litex/blob/master/litex/soc/integration/export.py)). The remaining dishonesty is timing, since Verilator is cycle-based and ticks are buffered by default to `limitBuffer` 1,000,000 ([co-simulating-custom-hdl](https://renode.readthedocs.io/en/latest/tutorials/co-simulating-custom-hdl.html)), and the twin must state that limit rather than hide it.

**RT1062 brings clock-tree and cache classes on an M7, with a sibling base.** `imxrt1064.repl` models LPUART, LPSPI, FlexSPI, GPT, eFlexPWM and ADC, but plain-Tags CCM with constant reads such as `CCM_CBCDR` = 0x000A8200, plus EDMA, XBAR1–3, ADC_ETC, QTimer, FlexCAN and LPI2C ([imxrt1064.repl](https://github.com/renode/renode/blob/c38ac3babcd38a7144b9498e3ca4c2226b76aa37/platforms/cpus/imxrt1064.repl)); an `NXP_eDMA` model landed in February 2026 but is not wired in ([NXP_eDMA.cs](https://github.com/renode/renode-infrastructure/blob/09ac7c563095c5410258ecc1b1a6b841a013db85/src/Emulator/Peripherals/Peripherals/DMA/NXP_eDMA.cs)). The cost to watch is documentation: NXP's i.MX RT reference manuals need a login ([NXP community](https://community.nxp.com/t5/i-MX-RT/Can-t-access-RT-1170-datasheets/td-p/1393124)), which collides with Tviburi's rule that every modeled behaviour cites the manual by revision and page.

### Phase 2 needs new platforms on cores Renode already has

Each phase-2 family adds one large, distinct failure class but needs new models. **STM32G4 is the analog and timing class**: HRTIM, COMP, OPAMP, CORDIC and FMAC, and **renode-infrastructure has no model of any of them** ([renode-infrastructure Peripherals](https://github.com/renode/renode-infrastructure/tree/master/src/Emulator/Peripherals/Peripherals)). It is also a cheaper rehearsal for motor control, because trip and comparator semantics can be built on a part with SVDs and Zephyr before facing C2000 or dsPIC. **STM32U5/H5 is the security-state class**: core-level TrustZone exists and was hardened in 1.17.0 with a secure-gateway check and HardFault escalation, yet `grep enableTrustZone` over `platforms/` returns nothing and no GTZC model exists ([CortexM.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Cores/Arm-M/CortexM.cs); [CHANGELOG.rst](https://github.com/renode/renode/blob/master/CHANGELOG.rst)). **nRF54L15 is the event-fabric class**: no DPPI model exists, and the DPPI `SUBSCRIBE`/`PUBLISH` hooks inside the existing nRF54 models are themselves Tagged ([NRF54H20_GRTC.cs](https://github.com/renode/renode-infrastructure/blob/09ac7c563095c5410258ecc1b1a6b841a013db85/src/Emulator/Peripherals/Peripherals/Timers/NRF54H20_GRTC.cs)), but DPPI is a contained peripheral, the DK costs $39 and the SVDs are public in nrfx ([nrfx mdk](https://github.com/NordicSemiconductor/nrfx/tree/master/bsp/stable/mdk)).

**RP2040 is the programmable-peripheral class**, and it can stay inside Renode by adopting matgla's MIT overlay. That overlay calls itself "WIP and Frozen (lack of time)" and runs PIO as an external C++ "additional CPU" where "manual synchronization is necessary" ([matgla/Renode_RP2040](https://github.com/matgla/Renode_RP2040)), so an honest twin must publish its scheduling quantum and refuse timing claims finer than it; rp2040js, with 1,225 lines of PIO and known gaps such as `clkDivRestart not implemented`, is a usable differential oracle ([rp2040js](https://github.com/wokwi/rp2040js)). **ESP32-S3 is the third-ISA and radio-refusal class**: upstream Renode has the Xtensa core with an `esp32s3` config and about six ESP32 models but no platform file ([renode-infrastructure Peripherals](https://github.com/renode/renode-infrastructure/tree/master/src/Emulator/Peripherals/Peripherals)), while Espressif's GPL-2.0 QEMU fork models far more, including GDMA, eFuse, crypto, TWAI and secure boot v2, and still not Wi-Fi or Bluetooth ([espressif/qemu](https://github.com/espressif/qemu); [Espressif blog](https://developer.espressif.com/blog/2026/09/zephyr-espressif-qemu-hello-world/)). That licence means porting by reimplementing from the TRM, never by translating QEMU code into MIT-licensed Renode. **AT32F435 is a Betaflight-only target worth adding for vendor divergence**: Betaflight carries a separate `src/platform/AT32` tree rather than reusing its STM32 drivers ([betaflight src/platform](https://github.com/betaflight/betaflight/tree/master/src/platform)), and Artery's own migration guide calls even its earlier F403A/407 line incompatible with the F435 ([MG0018](https://www.arterytek.com/download/MG/MG0018_Migrating_from_AT32F403A_407_to_AT32F435_437_EN_V2.0.3.pdf)). An "STM32F4 twin with renamed parts" would be exactly the silent substitution `INV-06` forbids.

### Phase 3 is everything Renode cannot host today

**C2000 has the highest value and the highest cost on the list.** The F28P65x carries 36 HRPWM channels at 150 ps, 11 CMPSS windowed comparators, 16 SDFM channels, a CLA coprocessor, lockstep on CPU2 and ISO 26262 ASIL B certification ([TI TMS320F28P650DK](https://www.ti.com/product/TMS320F28P650DK)); **none of those blocks exists in Renode, Renode has no C28x core, and TI dropped its CCS simulators around CCSv6** with staff saying there were no plans for more ([E2E 1305674](https://e2e.ti.com/support/microcontrollers/c2000-microcontrollers-group/c2000/f/c2000-microcontrollers-forum/1305674/simulator-for-c28x); [E2E 343311](https://e2e.ti.com/support/tools/code-composer-studio-group/ccs/f/code-composer-studio-forum/343311/simulators-removed-in-ccsv6)), so validation means silicon in the loop. **dsPIC33 is less ambitious but concrete, because the project holds Microchip's Drone 3S ESC**, built on the dsPIC33CDVC256MP506 SiP and running **sensorless trapezoidal** control with DC-bus over-current and over-voltage protection ([DS70005664A](https://onlinedocs.microchip.com/oxy/GUID-C9890415-1E03-4EA3-BFD3-F5CD4AB39257-en-US-1/GUID-5385504C-7322-491E-B7D4-6648D29A3C12.html)). Its register data exists only as Microchip's EDC `.PIC` XML, with no SVD or ATDF ([packs.download.microchip.com](https://packs.download.microchip.com/)), and MPLAB SIM fails the honesty test as an oracle, since with a bad stimulus file "the simulator will not notify you; it will simply ignore its contents" ([MPLAB SIM stimulus](https://onlinedocs.microchip.com/oxy/GUID-240F27AA-C615-4705-B68C-6E434B126B47-en-US-1/GUID-310471A3-B3EE-4633-AC8D-4348B11BB2DB.html)). The feasible route to either core is Renode's MSP430X precedent, a 1,659-line CPU written in C# outside tlib with GDB support ([MSP430X.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Peripherals/Peripherals/CPU/MSP430X/MSP430X.cs)).

**RP2350 is the one target nobody simulates.** Its datasheet lists dual Cortex-M33 or Hazard3 cores swapped at boot, 12 PIO state machines, 8 kB of OTP with signed boot, and a glitch detector ([RP2350 datasheet](https://pip.raspberrypi.com/documents/RP-008373-DS-rp2350-datasheet.pdf)), while Wokwi, the only simulator that runs a Pico 2 at all, simulates one M33 core, no Hazard3 and none of the new PIO instructions ([Wokwi Pico 2](https://docs.wokwi.com/parts/board-pi-pico-2)). **RT1176 has real flight-controller pull** through PX4's FMUv6X-RT, which PX4 says its maintenance and test teams support ([PX4 MR-VMU-RT1176](https://docs.px4.io/main/en/flight_controller/nxp_mr_vmu_rt1176)), but Renode has no dual-core machine for it and Zephyr's `vmu_rt1170` panics 13 of 13 on the dashboard ([dashboard results](https://zephyr-dashboard.renode.io/zephyr_sim/29d3d75b7ef638a5323815fa94f78af54c96d1a5/ad74f77c993b4d74659042852056f1bf811f152d/result-aggregated.json)). **nRF54H20 should wait**, since Zephyr says "all software for the nRF54H20 SoC is experimental and hardware availability is restricted to the participants in the limited sampling program" ([Zephyr nRF54H20 DK](https://docs.zephyrproject.org/boards/nordic/nrf54h20dk/doc/index.html)). **SAM E70 earns only an audit**: its `.repl` has not changed in substance since 2020 and hides gaps behind `ApplySVD` and a flip-flop stub on `PMC_SR` ([sam_e70.repl](https://github.com/renode/renode/blob/master/platforms/cpus/sam_e70.repl)).

## Six stock behaviours Tviburi must turn into named refusals

**The stock H7 tag list is the refusal list, already written down.** `stm32h7.repl` carries **38 sysbus Tags** that read zero and warn, covering RAMECC1/2/3, DMAMUX2, SAI1–4, VREF, COMP1/2, SPI1/2/3/5/6, the delay blocks, JPEG, MDMA, AXI GPV, WWDG1, SDMMC2, HASH, DCMI, HRTIM, DFSDM1, CAN_CCU, MDIOS, OPAMP, SWPMI, CRS, DAC1, HDMI-CEC and SPDIFRX1, and the USB OTG Tags at 0x40040000 and 0x40080000 sit on the same addresses as the `usb1` and `usb2` models ([stm32h7.repl](https://github.com/renode/renode/blob/master/platforms/cpus/stm32h7.repl)). Parsing every `Tag` in the pinned `.repl` chain gives a mechanical seed for Tviburi's refusal table. The trap is that **`ThrowExceptionIfNotTagged` would refuse none of those 38 regions, precisely because they are tagged**; plain `ThrowException` refuses them but also everything else, and can be scoped only through per-tag `throwException` ([SystemBus.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Main/Peripherals/Bus/SystemBus.cs)). The notes did not verify whether `BusAccessException` reaches the guest as a Cortex-M BusFault or as an emulator abort, but neither is a record on the logger channel, so **the stock throw does not satisfy `RUL-11` by itself** and Tviburi still has to emit the named record.

**Python stubs need their own honesty state, "canned".** The H7 PWR stub at 0x58024800 returns fixed CR1 = 0xF000C100, CSR1 = 0x6000 (ACTVOSRDY, "voltage level is valid"), CR3 = 0x4000000 (USB33RDY) and D3CR = 0x2000 (VOSRDY), and only logs for any other offset; the FMC stub reads zero for BCR0 and the SDRAM control registers ([stm32h7.repl](https://github.com/renode/renode/blob/master/platforms/cpus/stm32h7.repl)). **No wrong SMPS/LDO configuration or VOS sequence can ever fail in the stock twin.** The pattern recurs in the F746 (Python stubs for PWR_CR1/CSR1 and the LPTIM1 ISR, [stm32f746.repl](https://github.com/renode/renode/blob/master/platforms/cpus/stm32f746.repl)), the SAM E70 (a flip-flop on PMC_SR, [sam_e70.repl](https://github.com/renode/renode/blob/master/platforms/cpus/sam_e70.repl)) and the RT1064 (ticker and flip-flop stubs for WDOG, IOMUXC, ANALOG and DCDC, [imxrt1064.repl](https://github.com/renode/renode/blob/c38ac3babcd38a7144b9498e3ca4c2226b76aa37/platforms/cpus/imxrt1064.repl)). Tviburi's taxonomy therefore needs three states, modeled, absent and canned, with the last refused or flagged loudly.

**SVD loading serves reset values silently.** Before logging an untagged read, `SystemBus` consults any loaded SVD through `svdDevice.TryReadAccess`, so **an SVD-described register with no model returns its reset value instead of warning** ([SystemBus.cs](https://github.com/renode/renode-infrastructure/blob/master/src/Emulator/Main/Peripherals/Bus/SystemBus.cs)). Both `nrf52840.repl` and `sam_e70.repl` call `ApplySVD` ([nrf52840.repl](https://github.com/renode/renode/blob/master/platforms/cpus/nrf52840.repl); [sam_e70.repl](https://github.com/renode/renode/blob/master/platforms/cpus/sam_e70.repl)), which makes those stock twins quieter than they should be. Any Tviburi port to them must strip `ApplySVD`, or invert its use so the SVD supplies the names to refuse by rather than the values to serve.

**The Zephyr dashboard's generated platforms are anti-patterns, not starting points.** The generated RT1170 platform has one blanket Tag across 0x40000000–0x60000000 named after edma0, xbar1–3, lpadc, ccm and others, fixes `ANADIG_PLL_ARM_PLL_CTRL` at 0xF00000A6 and backs the PLLs with flip-flop stubs, so **firmware waiting for PLL lock always succeeds** ([generated RT1170 repl](https://zephyr-dashboard.renode.io/zephyr_sim/29d3d75b7ef638a5323815fa94f78af54c96d1a5/ad74f77c993b4d74659042852056f1bf811f152d/mimxrt1170_evk_b_mimxrt1176_cm7/hello_world/hello_world.repl)); the nRF54L15 platform Tags its DPPICs, radio, power and regulators the same way ([generated nRF54L15 repl](https://zephyr-dashboard.renode.io/zephyr_sim/29d3d75b7ef638a5323815fa94f78af54c96d1a5/ad74f77c993b4d74659042852056f1bf811f152d/nrf54l15dk_nrf54l15_cpuapp/hello_world/hello_world.repl)). The dashboard's 13 samples exercise only CPU, UART, timer, GPIO and LED ([dashboard config](https://zephyr-dashboard.renode.io/zephyr/29d3d75b7ef638a5323815fa94f78af54c96d1a5/config.json)), so **"926 of 1,513 platforms passing" measures how often firmware reaches hello-world, not fidelity** ([Antmicro blog](https://antmicro.com/blog/2026/08/recent-improvements-to-renode-zephyr-and-u-boot-dashboards)).

**LiteX's own generator drops what it does not know.** `litex_json2renode.py` prints "Skipping unsupported peripheral" for unknown cores and routes `ddrphy` and `sdram` to `generate_silencer`, which emits `SilenceRange` ([litex_json2renode.py](https://github.com/enjoy-digital/litex/blob/master/litex/tools/litex_json2renode.py)). A Tviburi wrapper must turn every skip into a named refusal and every silence into a declared region.

**Line-level facts must be re-read at the pinned tag.** The notes read Renode at master `c38ac3b` and renode-infrastructure at `09ac7c5`, whereas Aethelgard's own work-order feedback pins Renode 1.17.0 at `ab721d88` with Infrastructure `066a7f13` (`docs/work-orders/AET-WO-4300b.FEEDBACK.md`). Tag counts, line numbers and the `UnhandledAccessBehaviour` API need confirming against that pair before they enter a fact sheet.

## Rehosting research makes firmware proceed; nobody has built the inverse

The firmware-rehosting literature solves the opposite problem, inventing plausible peripheral answers so firmware keeps running for fuzzing. HALucinator replaces HAL functions with high-level emulation ([USENIX Sec 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/clements)); P2IM auto-models registers by access pattern and ran 79% of 70 images without manual help ([USENIX Sec 2020](https://www.usenix.org/conference/usenixsecurity20/presentation/feng)); µEmu answers unknown registers through symbolic execution and a knowledge base ([USENIX Sec 2021](https://www.usenix.org/conference/usenixsecurity21/presentation/zhou)); Fuzzware derives MMIO models from how firmware uses values and passed all 66 unit tests ([paper](https://sites.cs.ucsb.edu/~chris/research/doc/usenix22_fuzzware.pdf)); SEmu extracts condition-action rules from manuals ([arXiv 2208.07833](https://arxiv.org/pdf/2208.07833)); Perry synthesises models from drivers ([USENIX Sec 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/lei)); FlexEmu pairs structural primitives with a semantic model per peripheral class and reached 98.48% on 90 firmware ([arXiv 2509.07615](https://arxiv.org/abs/2509.07615)); and 2026's Reactive Peripheral Modeling treats peripherals as stateful event-condition-action systems ([arXiv 2608.29737](https://arxiv.org/abs/2608.29737)). The simulators share the default: QEMU's `unimplemented-device` "accepts all read and write accesses, treats them as read-as-zero and write-ignored, and logs each access as LOG_UNIMP" ([unimp.h](https://qemu.googlesource.com/qemu/+/refs/heads/stable-8.2/include/hw/misc/unimp.h)), which is Renode's posture too. **I found no system whose goal is to refuse unmodeled behaviour and report register coverage.** That is an absence of evidence after limited searching, since a sweep of DATE/DAC "virtual prototype coverage" work was not done, but the niche appears open.

Much of this work is reusable once its stance is inverted. P2IM's access-pattern classes and µEmu's per-access-point knowledge base identify exactly the status-register poll loops that rehosting auto-answers, which makes them detectors for where an honest twin must refuse. SEmu's condition-action rules and the event-condition-action formalism give each modeled behaviour a rule that can carry an RM revision and page, as Tviburi requires. FlexEmu's split into structure plus per-class semantics is the most plausible shape for a cross-vendor library, one UART, timer or DMA semantics instantiated per vendor. The P2IM unit tests and Fuzzware's 66 tests can serve as benchmarks. And SVD-to-model generation is proven by xPack's `xsvd`, which converts CMSIS SVD to QEMU peripheral code, though Peter Maydell raised SVD licensing against GPLv2 ([qemu-devel 2017](https://lists.gnu.org/archive/html/qemu-devel/2017-01/msg01253.html)) and Espressif QEMU's GPL-2.0 licence bars translating its models into Renode.

## Split out a separate twin at the first target Renode cannot host

The notes' synthesis sets three triggers for a separate, chipset-agnostic project: the target list includes a vendor Renode cannot host (today Espressif with no ESP platform, RP2040/RP2350 with no upstream model, and C28x/dsPIC with no core at all); refusal must hold uniformly across simulators, such as Renode plus Espressif QEMU, MPLAB SIM or Unicorn; or refusing maps must be generated from SVD for many parts instead of hand-written as subclasses of each stock model. Short of those, an SVD-generated overlay inside Renode is enough, combining bus-level `UnhandledAccessBehaviour` or per-tag `throwException` with generated refusing subclasses that emit `RUL-11` logger records.

**On the recommended order, that point arrives at the end of phase 2 or the start of phase 3, not before.** All of phases 0 and 1 sits on official or sibling Renode platforms, and most of phase 2 sits on Renode cores. ESP32-S3 is the first borderline case, because Renode has its core and a few models but the better oracle is Espressif QEMU, which pulls toward the second trigger; RP2040, dependent on a frozen third-party overlay, is the second. The first phase-3 commitment, whether dsPIC for the held ESC, C2000, RP2350 or ESP32-C6, trips the first trigger outright. Because Scotty intends to support all of these eventually, the split is a question of when, not whether, and **the decision point is concrete: start the separate repository when the first Renode-absent target is scheduled, or when any target needs a second simulator backend.**

What would be new in that repository is a **register-truth layer** and a **coverage report**. The layer would ingest vendor register descriptions (SVD for ST, Artery, Nordic, RP, Espressif and SAM; NXP's XML; Microchip's EDC for dsPIC; TI's TargetDB XML or C2000Ware headers; LiteX `csr.json`) and emit, per part, a complete map of every peripheral, register and field marked modeled, canned or refused, with refusals carrying their SVD names. The report would show which registers firmware touched, which were modeled and which refused, something none of the surveyed tools offers. Behaviour models would stay in each backend's native form, C# in Renode, C in QEMU, co-simulated RTL for LiteX, and the project would generate refusing wrappers per backend rather than reimplement any emulator. Renode has no native Rust peripheral API, so the Rust side (per `RUL-12`/`RUL-14`) would be a generator and analyser reaching Renode through emitted C# and `.repl` files, or through the DPI/TCP and SystemC co-simulation paths, which as of 1.17.0 let an external model throw a bus-access exception ([CHANGELOG.rst](https://raw.githubusercontent.com/renode/renode/master/CHANGELOG.rst)). A truly "Renode-like" new CPU simulator is only warranted for C28x and dsPIC, and the MSP430X precedent suggests even those are better contributed to Renode as C# cores. **One cheap step now makes the later split painless: keep Tviburi's refusal table as generated data keyed by SVD names, not hand-written C# lists**, so the overlay and the future project share one source of truth.

## RM0433: Rev 8 per ST's errata article, Rev 9 on Furnace

The two sources disagree, and this report does not choose between them. ST's community article on expected reference-manual updates, last updated 2026-10-02, lists **RM0433 at Rev 8 (January 2023)** as current, with pending corrections to the maximum ADC clock per voltage scale, the flash erase procedure, a **GPIOx_AFRH offset "0x2 to 0x4"** (September 2025) and RSS DTCM wording ([ST community](https://community.st.com/t5/stm32-mcus/stm32-mcu-reference-manuals-expected-preliminary-updates/ta-p/642051)). The project holds **RM0433 Rev 9** on Furnace as `rm0433-rev9.pdf`, sha256 `672a9433d6602da224e5215f571beed2be0e683cb025526f4afe9db61c26b6a0` (Aethelgard `spike/4240/ds/SHA256SUMS.st`), and already cites page-level content from it, such as §48.5.8 pp. 2035–2037 in `AET-WO-4300b.FEEDBACK.md`. The check is to read the revision-history table inside the held PDF, compare it with ST's live RM0433 documentation page ([STM32H7 docs](https://www.st.com/en/microcontrollers-microprocessors/stm32h7-series/documentation.html)), and confirm whether Rev 9 already carries the GPIOx_AFRH correction, which bears directly on alternate-function modeling. Until then, citations should keep giving revision and hash together, as they do now.

## Conclusion

The ranking turns less on what a chip can do than on where Renode's seams already lie. Every phase-0 and phase-1 target extends a platform Antmicro maintains, so Tviburi spends its effort on refusal rather than modelling, and each forces a different honesty mechanism: canned stubs (H7 PWR), radio timing limits written into model source (nRF52840), RTL timing limits (LiteX) and constant-valued clock trees (RT1062). By the end of phase 1 the refusal grammar will have been tested against four kinds of dishonesty rather than one chip, which is the evidence needed to know whether it can be generated from SVD.

The less obvious consequence concerns motor control, where Scotty's general co-design ambitions lead. C2000 and dsPIC are at once the most valuable and the least simulable families, and the held ESC makes dsPIC the more urgent. Building trip, comparator and PWM-fault semantics first on the STM32G4, a part Renode can host, and keeping the refusal table as vendor-neutral data, means the separate project will start with a tested refusal grammar and a library of motor-control semantics, leaving only the dsPIC and C28x CPU cores to build.
