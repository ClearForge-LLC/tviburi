## 1. Summary

**X scores 37/40 and Y scores 27/40. Merge X first, after the fixes listed in §5.**

Both outputs reproduce their own proof in the pinned image:
- X's `tests/spike.sh`: 9/9 checks, exit 0.
- Y's `renode/run-proof.sh`: exit 0, "TVI-WO-0100 proof ok".

Both use the same layout: an overlay `.repl` that `using`s the stock NUCLEO-H753ZI board, plus C# compiled at load time. Neither vendors Renode.

**X** wraps the stock `STM32H7_SPI` in a subclass at SPI1. Its rule is default-refuse and passes `CR1.SPE` only when its copy of CFG2 shows a mode fault is impossible. Its refusal record states the silicon claim together with its preconditions.

**X's weak points:**
- It widens SPI1 from a tag to stock fidelity.
- It has one disclosed false-pass route, IOLOCK (R8). I reproduced that the guard does not refuse it; that silicon would fault there is X's own from-memory claim.
- Raw Renode exits 0 on a refusal; only the runner returns 3.
- Its construction-time failures abort (exit 134) without the four fields.

**Y** puts a refuse-everything stub at SPI1. Every SPI1 access refuses, so its delivered surface has no silent path. Its weaknesses sit in the claims and the proof around that stub:
- **Silicon claim:** the refusal says a bare `SPE` write "raises MODF and clears MASTER", with no precondition. That restates the repo's own record of the scar (`repo-main/docs/architecture.md:19`), but without the configuration under which it happens.
- **Control:** its "modeled" control is the same `SPE` write on SPI4's stock model. Y's own FEEDBACK (`:62`, `:98`) records that SPI4's MODF is only tagged and still succeeds, so the control is a silent pass of the scar.
- **Harness:** the `--hide-log` assertion reads a fixed `/tmp` log, and I showed a stale copy alone satisfies it.
- **Shim removal:** with the shim removed, the Renode invocation exits 0.
- **Model hash:** it binds only a file named by an environment variable, and a hard-coded version string.

## 4. Beyond the rubric

### X

- **Defect: a consumer that runs Renode directly gets exit 0 on a refusal** (R9, `FEEDBACK.md:122`). The README says Aethelgard consumes Tviburi "the same way it consumes Renode today". If it keeps doing that, X's refusal is invisible at the exit code. Only `refusals.jsonl` or the runner carries the verdict. X discloses this, but it is the integration hazard most likely to recur.
- **Defect, minor:** the refusal's `virtual_time` is always `00:00:00.000000000` (quantum-granular, disclosed at `FEEDBACK.md:40`). Invariant 6 ("timestamp relative to virtual time") is not served by this field yet.
- **Overclaim, minor:** `FEEDBACK.md:30,37` quote PC `0x0800003E`, but the final code produces `0x0800002E`. Probably the removed BEFORE marker (`:91`) shifted the code; that is my inference. The quoted record is therefore not output of the committed code.
- **Gap:** the guard copies CFG2 even when the stock model drops the write (SPE=1). X says this yields only false refusals (`FEEDBACK.md:121`). I did not find a false pass from it beyond R8.
- **Stale doc:** `README.md:5` still says "No code yet. Phase 0".
- **Strength:** PASS requires positive evidence: the guard armed, the script reached its end, and the after-marker is present (`scripts/tviburi-spike:54`). That is why the stock model's silent pass is caught (run X1, stock). The seed is pinned (`scripts/prelude.resc:5`), and the record is byte-stable across runs.
- **Strength:** it fails closed on every load-time fault I tried (runs X2, X3, X6).
- **Strength:** it disclosed its own false-pass route and the surface widening instead of quietly patching them mid-spike, which is the flag-and-stop discipline the WO asks for.

### Y

- **Defect:** `Environment.Exit(1)` is called inside a bus access (`Tviburi_STM32H7_SPI1.cs:157`). Every proof drives the path from the monitor; no firmware or CPU access is ever exercised. So the refusal carries no PC, and the abrupt exit from a CPU-thread access is untested.
- **Defect:** exit 1 is Renode's generic failure code too. A consumer cannot tell a refusal from any other crash by exit status alone; only the log line distinguishes them.
