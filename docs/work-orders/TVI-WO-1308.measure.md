### P1. What silicon does (RM0433 Rev 9 and DS12117 Rev 10, from memory; §1 reads them)
- **DMAMUX1:** each of the 16 channels selects one of 107 inputs by `DMAREQ_ID` (0 none, 1–8 generators, then peripherals); synchronisation (`SE`, `SYNC_ID`, `SPOL`, `NBREQ`) and event generation (`EGE`) per channel; 8 request generators (`RGxCR`: `SIG_ID`, `GE`, `GPOL`, `GNBREQ`); overrun flags in `CSR`/`RGSR`, cleared through `CFR`/`RGCFR`. The registers are 32-bit access only (p708, as `1303` read it). Nothing in the chapter makes a `CxCR` write one-time; a channel may be re-routed at any time, and a route shared by two running streams is forbidden (p704).
- **PWR (RM0433, a device with no SMPS):** `CR3` holds `BYPASS`, `LDOEN`, `SCUEN` and the USB regulator (`USB33DEN`, `USBREGEN`, `USB33RDY`). **The supply configuration is written once after power-on; later writes are ignored until the next power-on reset** (from memory; whether a system reset re-opens it is to be read). `SDLEVEL`, which the WO names, belongs to the SMPS parts' manuals, **not** RM0433 (from memory; to be confirmed by search). `ACTVOSRDY` (`CSR1`) says the supply configuration is ready; `D3CR.VOS` reset is 01 (Scale 3), and `VOSRDY` rises after the regulator settles, with **no time stated in RM0433** (from memory) and perhaps none in DS12117. `CR1.DBP` = 0 at reset write-protects the backup domain (RCC `BDCR`, RTC, backup SRAM). The maximum clock per scale is a DS12117 table (rev V: Scale 1 400 MHz CPU / 200 MHz AXI, Scale 3 lower; from memory, low confidence on the numbers).

### P2. The stock models, by source (each probed in §1)
- **DMAMUX1:** a `CxCR` word write keeps `DMAREQ_ID` and drops every tag; a read returns `DMAREQ_ID` only. Byte and half-word writes are dropped (`BasicDoubleWordPeripheral`). A write with DMAMUX1's clock off is taken (the RCC guard locks only what it registers; DMAMUX1 registers on `sysbus`). Generators raise nothing.
- **PWR:** every write is dropped, with no log line for `CR1`, `CSR1`, `CR3`, `D3CR`, and an "Unhandled access" warning for every other offset (so `CR2` and `CPUCR` writes warn). `D3CR` reads `VOS` = 00 whatever was written; `CR3` reads `LDOEN` = 0 and `USB33RDY` = 1; `CSR1` reads `ACTVOSRDY` = 1 at once; `CR1` reads `DBP` = 1 before any write.

### P3. The generated firmware (14 boots, `1305`'s captures)
- **No DMAMUX1 access.** High (`1303a`).
- **No PWR write** (the queue's PWR rows are `ap5`-only). Moderate. **If so, they run at the reset scale (Scale 3) whatever their clock.** Their `sys_ck` is not known to me; if any boot raises `sys_ck` above Scale 3's limit (DS12117, from memory ~200 MHz on rev V), a scale rule refuses it on a path RM0433 says is invalid: a §7 stop and a row for Aethelgard. Low confidence; measured in §1 by computing each boot's AXI clock against Table 17's Scale 3 row.

### P4. ArduPilot, `sentinel-02-own` (the committed fixture, ELF `a799dfb6`, 5 s)
- **PWR, in this order, early in `stm32_init`:** `CR3` written once (`LDOEN`, `SCUEN` 0, `BYPASS` 0), `CSR1` polled for `ACTVOSRDY`, `D3CR` written `VOS` = 11, `D3CR` polled for `VOSRDY`, then the PLLs and `FLASH_ACR`; `CR1.DBP` set before the RCC's `BDCR`; `CR2` `BREN`; `CPUCR` written. **`CR3` is written a second time** later (`USB33DEN`, value `0x1000002`), and its `USB33RDY` polled. Moderate. **The second `CR3` write re-states `LDOEN` = 1 with the same supply bits**, so silicon's one-time rule ignores only what changes nothing. Moderate.
- **`CR1` is written tens of times** (`DBP` toggled around every backup-domain access: RTC, backup registers). High (`1150`: 93 writes in 5 s).
- **DMAMUX1:** the six streams `1303` measured, each `CxCR` a word write of a request id only (no `SE`, `EGE`, `SOIE`, generators, `RGxCR`, `CFR`). High.

### P5. The armed run (Sentinel-03, 14 s)
- **PWR:** as P4, plus nothing new after the arm. `D3CR` = `VOS` 11 before the PLL lock and before `FLASH_ACR`'s latency rises. High.
- **DMAMUX1:** ten channels; **some `CxCR` rewritten many times** (ArduPilot's shared-DMA locks re-allocate a stream per bus transfer, and ChibiOS writes the route at each allocation), every value a peripheral request id, none 0 written while its stream runs. Moderate on the count, high on the values.

- **The console:** the stub's "Unhandled access" warnings for `CR2`/`CPUCR` (and any other offset) disappear or change text once PWR is guarded. Aethelgard reads console records by source; a warning line is not a record, so no gate moves. Moderate.

Moderate.

### P7. Cost
- **Memory:** two small guards in the one file: **+8 to +20 MiB** at the median of eleven boots a side (`1302`'s compile-garbage effect dominates; two classes of a few hundred lines). Under `1201`'s budget. Moderate.

### P8. Form
- **DMAMUX1 can be guarded by a subclass** (not sealed), which keeps the DMA guard's `dmamux` property typed `STM32_DMAMUX` and its direct `ReadDoubleWord` calls working. A wrapper (the WO's word) would need the DMA guard's property re-typed, outside this fence: a ruling question. ### 2.3 What the DMA guard's start check already reads

At each stream's `EN` rise, `GuardedSTM32DMA.RefusedRoute` (`model/GuardedSTM32DMA.cs` L694–757) reads `DMAREQ_ID` from `dmamux.ReadDoubleWord(4 * ch)` on the object it was handed (`dmamux`, typed `STM32_DMAMUX`) and refuses: `TVI-DMA-ROUTE` (0 or reserved), `TVI-DMA-MUX` (a generator id), `TVI-DMA-SHARED` (the same id on another running channel, p704), `TVI-DMA-REQUEST` (an id no model raises). **It never compares the route with the stream's `PAR`,** so a stream whose route names another peripheral's request starts silently. **It reads the channel through a direct C# call,** which a subclass guard serves (the call is virtual, R) and a wrapper of another type cannot (the property is typed `STM32_DMAMUX`). **It never sees a `CxCR` rewritten while its stream runs** (`1303` FEEDBACK §7).

## 4. The form (F, R)

- **DMAMUX1 is guardable by a subclass** (R: `STM32_DMAMUX` is public and not sealed; `ReadDoubleWord`/`WriteDoubleWord` virtual and not final). A subclass keeps the DMA guards' `dmamux` property (typed `STM32_DMAMUX`) and their direct `ReadDoubleWord` call, which then reaches the guard. **A wrapper, the WO's word, cannot be handed to the DMA guards** without re-typing their property, which is outside this fence (§6 Q1).
- **No typed redeclaration exists** (`RUL-09` (b)), so the stock entry is cancelled and the guard declared at `0x40020800` `as "dmamux1"`, with the stock entry's three properties and its sixteen routes onto `tviburiDma1`/`tviburiDma2`. **Every reference to the variable `dmamux1` must then be restated:**
  - the DMA guards' `dmamux: dmamux1` and the ADC guards' `dmaPeripheral: dmamux1` (their restate files);
  - the consumer's own `DMARecieve -> dmamux1@37`/`@39` (`spi1`, `spi2`) and `1305`'s `ReceiveDmaRequest -> dmamux1@41` (the replay's stand-in);
  - two stock lines: `spi4`'s `DMARecieve -> dmamux1@83` (`stm32h7.repl` L197) and `crypto`'s `OutDMA -> dmamux1@77` (`stm32h753.repl` L5).

  F repointed the platform's own references and **left the two stock lines unrestated: the platform loaded with no error** (Renode exits 0 either way). So an unrestated reference fails silently, the `RUL-09` (b) trap again; neither `spi4` nor `crypto` is used by any replay.
- **PWR has no stock C# model to subclass or wrap.** The guard is a Tviburi-authored peripheral; `pwr` is cancelled and the guard declared `as "pwr"`. **On the 14 generated platforms, the consumer's own `pwr:` script update binds to the cancelled entry and is dropped with no error** (F: the probe ran, the script did not). The consumer's script and the guard model the same two rules; the guard must supersede it (§6 Q13).
- **F's result:** with both probes restated, **all 16 replays are line-for-line identical to `main`** (4,553,427 lines on the armed run; every MAVLink frame, the arm at 9.332 s, every access line with its register name, the boot block), **except four lines of the `peripherals` listing:** `dmamux1 (STM32_DMAMUX)` → `(ProbeDmamux)` and `pwr (PythonPeripheral)` → `(ProbePwr)`. The probe's copy of the stock register enum keeps DMAMUX1's access-log names; PWR's are `unknown` in both (the stub has none).

## 6. Ruling questions, with my recommendations

**DMAMUX1**
- **Q1, the form.** A **subclass** of `STM32_DMAMUX` (not the WO's "wrapper"), re-implementing the three bus interfaces (`RUL-07`'s default; the wrapper is for a sealed model), cancelled and restated `as "dmamux1"` by a generated `model/stm32h7-dmamux-restate.repl`. It restates the stock routes and the four stock-file references (§4) **by untyped updates in its own file** (`tviburiDma1: dmamux: tviburiDmamux1`, `tviburiAdc12: dmaPeripheral: …`, `spi4: DMARecieve -> …@83`, `crypto: OutDMA -> …@77`), so no other guard's restate file changes. F measured the repointing by rewriting the platform; the untyped-update form is the build's first measurement, and a stop if it does not hold. **A row for the consumer and for `1203`'s class map:** a platform's own `-> dmamux1@N` lines must be repointed, or they bind to the cancelled entry silently. **Recommend: yes.**
- **Q2, sub-word access.** Silicon takes byte and half-word writes (p708); the stock model drops them (S). **Recommend:** modeled, merged into the guard's copy and passed to the stock model as a word. No measured firmware uses one, so no replay moves.
- **Q3, a route that names another request (WO acceptance 1).** The judgement needs the stream's `PAR` at its `EN` rise, which only the DMA guard sees: ArduPilot writes `CxCR` *before* `PAR` (§2.1), so a judgement at the `CxCR` write would read a stale `PAR`. **Recommend: grant a one-call addition to the DMA guard** (as `1307` Q8 granted one query): at its existing route check it asks the DMAMUX guard to judge `(channel, PAR, direction)`. The DMAMUX guard holds the table: each id the twin raises or acknowledges (the DMA guard's `RaisedToMemory`/`RaisedFromMemory`) → its peripheral's data register (Table 124 p697–698; each peripheral's base, Table 8 p134; its data register's offset by page). **Kind: `unmodeled`**: silicon would pace the stream by the named request and move to or from `PAR` as written, so it is not a fault by any page; the twin pairs each request with its own peripheral and was never checked on another pairing. (The alternative, `predicted-fault`, has no page saying silicon misbehaves.) Every measured stream passes (§2.1). **A route the platform cannot raise** stays the DMA guard's existing `TVI-DMA-REQUEST`/`TVI-DMA-ROUTE` at `EN` (a route nothing starts is harmless); the DMAMUX guard adds only the reserved-id refusal at the write (§2.2). **Also:** a `CxCR` rewritten to another id while its stream runs (now visible to the guard, through the DMA guard's public `StreamState`) refuses `unmodeled`; a rewrite with the same id passes (ArduPilot's 77,402 rewrites).
- **Q4, clock and reset.** A write with `DMA1EN` = `DMA2EN` = 0 is dropped and a read returns 0, as the RCC guard does for every unclocked peripheral ("A write access will be ignored", p373; p455): read through the RCC guard's public `ReadDoubleWord(0x0D8)` (its `AHB1ENR`, which logs nothing when read through the object), no RCC edit. `DMA1RST`/`DMA2RST` reset the guard and the stock channels (p433), through the RCC guard's existing `Written` event (`1304`'s), as a second subscriber. **Recommend: yes, both modeled;** no replay moves (§2.1: clocked at every write; the reset pulse precedes every route).

**PWR**
- **Q5, `VOSRDY`, `ACTVOSRDY` and `USB33RDY` have no stated time** (RM0433 and DS12117 searched, `rm/rules.md` P4, P9). The WO says `unmodeled` "if no figure is stated". **Taken literally, every `VOS` write refuses: all 14 generated boots, the fixture and the armed run (a WO §7 stop: the armed run would refuse on a path RM0433 says is valid).** **Recommend:** each rises at the write that makes it due (`ACTVOSRDY` at the valid supply configuration, `VOSRDY` at the `VOS` write, `USB33RDY` at `USB33DEN`), **acknowledged by name** in the ledger ("no figure in RM0433 Rev 9 or DS12117 Rev 10"), so the polls end at once, as both platforms' models answer today. "A clock raised before `VOSRDY`" then reduces to "a clock above the scale in force" (Q9).
- **Q6, the one-time write.** **Recommend:** a later write that leaves the lower byte unchanged passes (silicon ignores it and nothing changes, `RUL-18` as amended: ArduPilot's second write); one that changes it is ignored and recorded **`predicted-fault`** (silicon ignores what the firmware wrote, p308), in both modes: in recorded mode the record is `would-refuse` and the write is still ignored, because ignoring it is the model, not a stock pass-through. An invalid `LDOEN`/`BYPASS` pair locks the register and leaves `ACTVOSRDY` 0 (p308), `predicted-fault`. The state survives `machine Reset` ("This register is reset only by POR. It is not reset by wakeup from Standby mode and by the RESET pad", p307), although p265 says "After a system reset, the software shall configure the used supply configuration in PWR_CR3": I read p265 as "configure it, once, before VOS" and p307 as deciding what a reset clears. **Ruling asked on that reading,** because the adversarial pass targets exactly this reset.
- **Q7, the silicon revision.** `CR3`'s reset value (rev V `0x46`, rev Y `0x06`, p307) and the scale's limits (rev Y: no VOS0, no AHB/APB rows, DS12117 p129–130) depend on it. **Recommend:** a required `revision` property, as the ADC guard's (`1307` Q2), the replays declaring "V". **And ArduPilot writes the lower byte `0x02` on rev V,** clearing bit 6, which reset sets and RM0433 calls reserved ("must be kept at reset value", p308); the generated firmware keeps it (`0x42`). **Recommend:** acknowledged by name for bit 6 on rev V only, as `1307` Q6/Q7/Q14 did for ArduPilot's measured patterns; otherwise `unmodeled` refuses the fixture and the armed run (WO §7).
- **Q8** is folded into Q5 (`USB33RDY`).
- **Q9, who reads the scale, and the clock rule.**
  - **The flash guard** reads `D3CR` through the bus object today (`model/GuardedSTM32H7_Flash.cs` L510–520). **Recommend:** it asks the PWR guard's public `Scale`; on a platform with no PWR guard, the scale is "unknown", decided at VOS1 and acknowledged as `1304` ruled.
  - **The RCC guard** gains one rule, `TVI-RCC-VOS`, at its existing clock trial (each write that changes `sys_ck`, `D1CPRE`, `HPRE` or a `PPRE`): CPU, AHB or APB above DS12117 Rev 10 p210's limit for the scale in force (at VOS3, APB 50 MHz applies "when at least one peripheral is enabled": footnote 6 sits on the VOS3 cell only in the text layer, to be checked on the rendered page in the build); above VOS1's CPU limit, `unmodeled` (VOS0 needs `ODEN`, which the stock SYSCFG does not hold). **And the PWR guard** judges a `VOS` write that lowers the scale below the clocks then running (p310's second sentence). **Kind: `predicted-fault`**, citing p310 ("shall"), p286 ("otherwise the system might be unreliable") and DS12117 p210, with a bench-check row. This is more than the fence's "voltage-scale read": **grant it, or narrow the rule.** Every replay passes (§3.1: Scale 2 at 64 MHz; Scale 1 at exactly 400/200/100 MHz). Table 60's per-peripheral kernel-clock maxima by scale (p354) are a row, not built.
- **Q10, `DBP`.** The PWR guard gates its own `CR2`. **`RCC_BDCR`'s protection lives in the RCC guard,** whose ledger rows say today "the twin's PWR is a canned stub that reads DBP = 1 (acknowledged by name)": that text becomes false. **Recommend: grant one RCC read** of the PWR guard's `DBP`: a `BDCR` write with `DBP` 0 refuses `unmodeled` (RM0433 says "write-protected", never what the write does, p427). ArduPilot writes `BDCR` only with `DBP` 1 (§3.1). The RTC's registers and backup SRAM are unguarded: a row.
- **Q11, `CR1` bits 31:28.** The printed reset value is `0xF000 C000` (p304), the map's `0x0000 C000` (p313), and the bits are "Reserved". ArduPilot writes `1111`, the printed reset value. **Recommend:** allowed as `{0x0, 0xF}`, citing both pages, and served as written.
- **Q12, ArduPilot's `BREN` written with `DBP` 0** (§3.1). RM0433: `CR2` is write-protected until `DBP` (p306), effect not stated. Silicon would leave `BREN` 0 (as protected); ArduPilot never polls `BRRDY`. **Recommend:** acknowledged by name for ArduPilot's measured write, the write not taken, with an upstream row (a ChibiOS order: `CR2` before `DBP`; the line cited in the build from the pinned ArduPilot image). Otherwise the fixture and the armed run refuse (WO §7).
- **Q13, PWR's form.** A Tviburi-authored model, cancel and restate. **Rows for Aethelgard:** its generated platforms' own `pwr:` script is dropped by the cancel (F) and the guard supersedes it; its foreign platforms have no PWR model of their own. **Recommend: yes.**

**Both**
- **Q14, the observers that move** (WO §7): on every replay, two `peripherals` lines name the new types (§4), as each earlier guard's did; on the fixture and the armed run, the stub's two "Unhandled access" warnings (`CR2`, `CPUCR`) go, because the guard models both registers. No record, boot block, MAVLink frame or access line moves in F (a pass-through). **The built PWR guard will also move served values on the two stub platforms,** predicted, none read by the boot block (checked on all 16 argvs: no PWR or DMAMUX1 read) and none changing a branch ArduPilot takes: `D3CR` reads `0xE000` after its write instead of `0x2000` (`VOS` 11 kept); `CR1`'s read after the `0xF000C000` write reads `DBP` 0 instead of 1 (ArduPilot then ORs `DBP` in either way); `CR3`'s `USB33RDY` per Q5 (never read on that path). On the generated platforms the guard serves what the consumer's script serves today (§3.1). Aethelgard's other observers were not re-read in this work order: its judge reads records, the boot block and MAVLink, as the earlier guards' work orders measured. **Recommend: accepted, named in FEEDBACK.**
- **Q15, the manifest.** `1203`'s rule (an instance restated only once a replay has run it guarded) has not landed. **Plan:** build both guards' replays first, then add `dmamux1` and `pwr` through `1203`'s API after merging `main`.
- **Q16, the eleventh shard.** WO §7: the projection passes 20 minutes on the WO's formula (21.4 min), not on `main`'s calibration (18.7 min). **Recommend: the eleventh shard first,** as its own commit, `times.tsv` re-weighed from `main`'s last code CI (as `1307` did for the tenth), then this work order's rows re-weighed from its own CI run.
