**Q3, WO (4): no default crystal.**

- **`TVI-RCC-HSE`, `unmodeled`:** a `CR` write that sets `HSEON` on such a platform (p384; the HSE described §8.5.2 p339). It is evaluated first among the write rules.

**Q4, WO (5): `RTCEN`.**
- **The architect's premise, corrected at the ruling:** `RTCEN` gates `rtc_ck`, while the RTC's registers are gated by `RTCAPBEN`, 1 at reset (p366, p471). So "locked as silicon locks it" means never locked.
- **The copy:** `RTCEN` is served from the guard's copy, 0 at construction (a power-on is a backup-domain reset, p427, p334) and kept across a machine `Reset` (p427). Writes of 0 and 1 are taken.
- **The stock model's `RTCEN` is always written 1,** so `rtc` stays unlocked. That also fixes the latent lock: before, any `BDCR` write the allow-list passed (all zeros) locked `rtc`.
- **Safe while two things hold:**
  - `RTCSEL` is held at 00 by its row ("No clock", p427), so `rtc_ck` has no source whatever `RTCEN` says;
  - `DBP`, `BDCR`'s write protection (p427), is not modeled: the twin's PWR is a canned stub that reads `DBP` = 1. That is acknowledged by name in the row.
  - The row's class is "inherited, unaudited (acknowledged by name)", as the `*ENR` copy rows are.
- **Planted:**
  - `firmware/rcc.rs` `rtcen`: ArduPilot's `set_rtc_backup` order (`BDCR` written 0, an RTC backup register written and read back, `RTCEN` written 1). The planted `BDCR` write of 0 leaves the backup register readable (`rcc-rtcen`).
  - `rcc-rtcen-reset`: read 0 at construction, 1 kept across `machine Reset`, written back to 0 with `rtc` unlocked.
